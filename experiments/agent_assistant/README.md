# SAWA 業務アシスタント・隔離試用

## stgでの実行

`agent_runtime/Dockerfile`は3業務の固定ソースと明示した試用baselineを同梱します。hospitalは同じdevelopのbackend/ocr_pipeline、shiftとschool-lunchは`agent_runtime/manifests`に元SHA・差分digest・全ファイルhashを記録したsnapshotです。source manifestの不一致は起動を拒否します。病院の初期データは清潔な正式fixtureと原本です。各依頼の準備中に宣言済み原本を正規サービスでpending登録し、その依頼専用の配送契約ごとbeforeを封印します。保存済み契約のroot・credential digestをコピー先向けに書き換えません。

既存のstg Actionsがweb-stgの非公開sidecarとして配置します。Nextの認証済みproxyだけが接続トークンを付け、登録済み試用担当者と業務権限をPortalへ照合します。新しいIAM権限・公開agent endpoint・認証省略はありません。Claude未設定時は利用不可として表示し、キーがあるGeminiを初期接続先とします。料金単価は実行開始時に記録し、管理画面に概算額として表示します。

業務正規schema（public）を変更せず、専用schemaの`sawa_agent_trial.ledger`行をロックして台帳を保存します。既存SQLiteスキーマをbyteaへ直列化し、SQLiteファイルをネットワークvolumeで共有しません。依頼開始前のコピー、原本添付、質問図面、取得帳票は`sawa_agent_trial.files`へ保存します。既存業務tableを復元で書き換えません。

作業中の各業務DBは依頼専用の一時コピーです。再起動・revision交代時は前instanceをepochで拒否し、非終端依頼を「結果の照合が必要」へ移します。途中処理を再送せず、料金・予約・遠隔実行IDを保持します。利用者は履歴から停止・元に戻す操作ができます。再起動後の原本・帳票はhashを照合して復元します。月次上限は初期0のまま管理者が管理画面で設定します。


専用ブランチ `codex/agent-assistant-trial-20261019` の未コミット実装です。developへの統合、push、stg/prod反映は行っていません。

## 選択業務の証跡・入力修復（2026-10-20）

病院・シフトも学校給食と同じく、内部版・シート・証跡IDをモデルへ転記させずサーバーが管理する。`prepare_shift_review`は選択月の条件・正規勤務期間・OR-Tools・検査結果を承認画面へ提出し、`complete_shift_work`は人の承認後にその候補だけ確定・Excel出力・保存結果を再照合する。欠勤時は指定された職員と日付のunavailable/hardだけを追加し、既存条件は保持する。

`prepare_fax_review`は対象FAXの原本PDFと全数量行を返す。モデルは原本を画像で読み、業務上の不明点を質問して`request_fax_approval`へ照合結果を提出する。変更しない正本シートの転記は不要。`complete_fax_work`は全対象の人の承認を確認してから、通常の数量検査・確認記録・保存・袋分け・確定・正規三帳票・受領内容照合を通す。認識値・承認・nativeの版検査を省略しない。

MCPの送信結果は48,000文字を超える場合に保存証跡への参照を返す。完全なnative結果は台帳に保持し、`read_tool_result`のJSON Pointerと一覧ページで必要な箇所を取得できる。承認・完了判定は完全な正本を使う。FastMCPの実行前入力検証エラーは実行なしの修復可能な結果としてモデルへ戻し、通信中断・認証・未確定書込みを入力ミスとして再送しない。確定後の一覧の更新は承認した勤務案のconfirmed/confirmed_atだけ許可し、勤務内容・他の勤務案の変更は引き続き承認失効となる。

FAXの進捗再取得は、取得開始時のstate・review・decisionが同じ場合だけ反映する。OCR完了・承認待ちのバックグラウンド更新が、新しい承認・訂正回答を上書きしない。価格の訂正保存は正規APIが返したdraft_idと成功した命令IDで日次業務の選択を更新し、過去の生成分と取り違えない。内部ドラフトIDを利用者へ選ばせない。MCPの大きな結果でも、FAX全対象の状態・利用者回答と、レビューの状態は内容を変えずに残す。

実施価格の税込単価・税抜単価の同時指定は、nativeの計算契約と同じ排他検証を保存前に行う。スキーマにも明示し、回答済み金額・税率を変えずにモデルが形式だけ修正できるようにする。既存価格の取得で同じ形式エラーが返る場合も、一般的なAPI拒否の質問にせずモデルへ入力エラーを返す。認証・競合・不明な実行結果はこの扱いにしない。

## 実装範囲

- SAWAのシステム選択から「AIに依頼」へ入り、選択式の定型業務・確認回答・原本添付・出力取得を行うページ。自由記述は初回依頼の主操作にせず、確認事項への回答に使います。
- Claude **Managed Agents API**による実行。独自のモデル推論ループやClaude Code常駐は不要です。ローカル側は業務ツールの実行、停止、履歴、予算管理を担当します。
- 既存APIへつなぐ105操作（病院42・シフト26・学校給食37）と、スキーマ取得・確認質問・原本画像取得・配送状態取得・完了証跡・FAXキュー・FAX確認提出・FAX待機・定型業務の対象取得・承認提出・承認待機・ジョブ待機の13ツール（図面の確認回答採用を含む）。任意URL・SQL・シェルは公開しません。
- Streamable HTTP MCPとClaude用の非公開カスタムツール橋渡しは、同じFastMCPの入力検証・実装を通ります。Claudeのクラウドからlocalhostへ直接接続させる構成ではありません。公開トンネルは不要です。
- 依頼と命令の重複防止、受信イベント、API結果、入力根拠、料金、出力ハッシュのSQLite記録。
- API拒否・版競合・認証切れは確認待ちにします。確認質問のツール結果は、人が回答するまでClaudeへ返しません。
- 料金はClaudeが返す累積`list_cost`をセントで記帳します。同じ通知を二重加算しません。月次予約と依頼別のプロバイダー予算を設定します。初期予算は0です。

## 操作の流れ

1. SAWAへログインし「AIに依頼」で業務・作業項目・依頼予算を選択します。病院3・シフト5・学校給食5の13項目を選択できます。対象一覧は試用基準データの専用コピーを既存APIで読み、先頭候補の自動採用を行いません。
2. サーバーが利用権限と月次予算を確認し、その依頼用にDB・ファイルを複製します。Claudeセッションにも依頼予算を設定します。
3. Claudeが操作スキーマと保存状態を取得し、既存APIで業務を進めます。数量計算・袋分け・OR-Tools計算・既存OCRはSAWA側を利用します。
4. 原本や判断が必要なら確認待ちになります。利用者が原本の施設・期間を確認して添付し、回答すると、その保留中のツール呼出しへ回答を返して続行します。
5. 保存後のGET、対象ID、未解決blocker、配送結果、成果物ハッシュを確認して完了申告を記録します。受付・ジョブ開始・idleだけでは完了にしません。完了申告と実行証跡を画面に併記します。指示内容との意味的な一致まで保証する機構ではありません。
6. 「停止」は命令世代を先に無効化し、起動途中の処理もキャンセルし、専用API/workerを終了・回収します。Claude側もinterrupt・停止照会・archiveを行います。遠隔停止の結果が不明なら予約額を保持します。
7. 「この依頼を元に戻す」は停止後に依頼用コピーを開始前へ戻します。変更後コピー・履歴は保存し、旧成果物の配布を止めます。繰り返し押しても再復元しません。

本番・stgや共有DBを復元で上書きしません。既存環境への反映機能はありません。API料金は取り消せません。管理者がOCRクラウド接続を明示設定した場合のOCR出力オブジェクトも削除しません。

- `GET /tasks`の公開定義から作業を選択し、`POST /runs`へ`task_id=hospital_pending_faxes`を送ります。内部手順と業務権限の範囲はサーバーで定義し、同時に自由な指示を差し込む要求は拒否します。

### 対象と確認の保存

- `POST /tasks/{task_id}/targets`はSAWA権限を確認し、専用コピーを起動してネイティブGETから対象一覧を取得します。読取コピーは停止・回収し、選択IDと一覧を台帳へ保存します。モデル呼出し・料金予約は行いません。
- 新規依頼は`selection_id`・`target_keys`・必要な`layout_id`を送ります。一覧外のID、他校、他月、別候補、同じ日の献立の部分選択、未選択の図面を拒否します。
- シフトに新規`GET /planning/period`を追加し、既存ソルバーと同じ設定・期間解決関数を使います。固定開始日の期間を暦月へ置き換えません。欠勤日もその正規期間で検査します。
- `get_task_context`で選択内容を取得し、`request_task_approval`へ成功したネイティブGETの命令ID・確認結果・正確な確定予定内容を提出します。提出時に既読結果との一致を再取得で照合し、モデルが古い結果を見たまま確認カードを出すことを防ぎます。
- 確認画面はモデルの説明と実データを表示します。勤務表、検査、不足、献立、工程表、動線図、原本セル画像、発注案を展開できます。50件を超える配列も前後ページで全件確認でき、値を切り捨てません。0を空欄にしません。
- `POST /runs/{id}/decision`は人の画面専用です。承認ID・入力と結果の署名を再照合します。`wait_for_task_decision`は書込みlockを保持せず、承認・訂正・停止を受け付けます。非同期ジョブも`wait_for_native_job`でサーバー内待機します。
- 承認前のシフト確定・原本認識採用・献立取込確定を拒否します。承認したID/query/bodyだけを一度実行し、nativeの版・preconditionもそのまま要求します。承認後に追加の編集・再計算をした場合は再確認へ戻します。
- 学校給食は既存`get_schedule_draft`と保存・動線図APIを使います。工程表・動線図の元データが変わっている場合、欠落日がある場合、在庫・価格・単位・発注先が不足する場合に完了しません。出力には確認済みID・版・学校・日付・図面版の`expected_sources`を必須にし、受信後にも入力を照合します。
- 原本取込は学校・月の選択後、原本添付待ちになります。選択と一致すると利用者が照合した添付を受け付け、添付後に初めてClaudeを開始します。原本待ちの停止・復元・料金表示も、未確定の遠隔作成と区別します。
- 不足・違反の「検査報告」では問題そのものを隠しません。失敗して候補がない勤務案も、候補を捏造せず失敗理由の報告として確認・完了できます。勤務の確定・出力とは区別します。
- 要確認FAXは原本セルの認識訂正または再処理に個別承認を必要とし、復旧後の数量表にも別の確認を要求します。確認済みのネイティブ確定snapshotがある場合だけ、歴史的な失敗ジョブを新たな未完了と誤判定しません。元のOCR・取込失敗履歴は書き換えません。
- 完了には全選択対象・確定予定操作・承認後の全帳票と再取得が必要です。`停止`は世代を無効化し、復元は専用コピーだけを開始前へ戻します。確認履歴・利用料金は保持し、復元後の承認回答と旧出力配布を拒否します。
