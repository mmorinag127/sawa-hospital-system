# 権限再監査と実運用演習レビュー 2026-03-12

## 対象
- 権限境界の再確認
- ユーザー1: 注文確認から発送まで
- ユーザー2: 注文書準備、月次メニュー、注文書アップロード
- 管理者: システム保守、ユーザー管理、破壊的操作

## 結論
- backend の API 権限は、直近修正後は大きくは崩れていない
- ただし frontend 表示は `ユーザー1 / ユーザー2 / 管理者` の3区分で見せている一方、backend 実ロールは `operator / admin` の2区分しかない
- そのため、画面上の期待権限と実際の権限が一致していない
- 実運用で一番危険なのは、`月次メニュー未登録でも Step2/確定まで進めてしまえること` と `admin 専用操作が operator に見えていること`

## 優先度高

### 1. frontend に実ロール判定がなく、全ナビが見える
- 現状:
  - ログインしていれば `TopNav` の `ユーザー1 / ユーザー2 / 管理者` を全部見られる
  - backend の実ロールは `operator / admin` だけ
- リスク:
  - operator が `管理者` ナビを見て、操作してから 403 を受ける
  - 実際にできることと、見た目の期待がずれる
- 改善案:
  - `/auth/me` 相当で現在ロールを返す
  - `TopNav` は `operator` と `admin` で表示を分ける
  - `ユーザー1 / ユーザー2` は運用グループ表示として残してもよいが、backend 権限とは切り分けて明記する

### 2. 月次メニュー未登録でも OCR fallback のまま確定に進める
- 現状:
  - `sheet_weekly_menu_missing` は警告で出る
  - ただし Step2 から先へ進める
  - `ocr_table` 由来の暫定シートでも反映・確定まで行ける
- リスク:
  - 正しい週次メニュー土台がないまま、崩れたシートを確定する
- 改善案:
  - `sheet_weekly_menu_missing` 中は確定をブロック
  - バナーに対象月メニュー画面への直リンクを出す
  - `この警告を解消しないと確定できません` を明記する

### 3. 注文詳細の Step 前提条件が遅い
- 現状:
  - Step2 以降へ画面上は進める
  - 実際には施設・週が未設定だと後段で止まる
- リスク:
  - 「進めたのに何もできない」体験になる
  - 中小企業の初回利用者には分かりづらい
- 改善案:
  - Step2 以降を未達条件時は disabled 表示
  - タブ自体に不足条件を短く出す
  - 例: `施設未設定`, `週未設定`, `月次メニュー未登録`

## 優先度中

### 4. admin 専用操作が混在ページに並ぶ
- 対象:
  - システム管理
  - 送り状履歴
  - 注文詳細の施設設定書き戻し
- リスク:
  - operator が普通に押して 403 になる
  - どこまで触ってよいか学習コストが高い
- 改善案:
  - admin 専用ボタンを折りたたみ、または `管理者専用` バッジ付きにする
  - operator にはボタン自体を隠すか disabled にする

### 5. 注文書アップロード後の次の行動が弱い
- 現状:
  - upload 成功後に message_id 中心
  - 既存注文への deep link が弱い
  - OCR 完了までの追跡も弱い
- リスク:
  - ユーザー2 が次にどこを見るべきか迷う
- 改善案:
  - `注文を見る` ボタン
  - `既存注文を開く` ボタン
  - OCR 状態の自動ポーリング

### 6. 施設一覧は初心者向け UI になっていない
- 現状:
  - 実質的に master JSON 編集に近い
- リスク:
  - ユーザー2 には重い
- 改善案:
  - 施設名、別名、区分、納品書設定などをフォーム化
  - JSON は上級者用に分離

## 優先度低

### 7. ダッシュボードと一覧の完了条件説明が薄い
- 現状:
  - 案内はあるが、完了条件が短くまとまっていない
- 改善案:
  - 各画面に `この画面で終わればよい状態` を1行で追加

### 8. 監視と例外対応が運用文書にまだ弱い
- 現状:
  - runbook はあるが、毎日誰が何を見るかが散っている
- 改善案:
  - `朝の確認`, `異常時`, `月初` の3章にまとめる

## 仮想運用での詰まりポイント

### ユーザー1
1. 注文一覧を開く
2. 対象注文へ入る
3. Step1 で施設・週を確認
4. Step2 で OCR 修正
5. Step3 以降で確認・確定

詰まり:
- Step1 未完了のまま Step2/3 を触ろうとする
- 月次メニューが無いのに暫定シートで進めてしまう
- OCR fallback と正式シートの違いが分かりづらい

### ユーザー2
1. 月次メニュー登録
2. 施設設定確認
3. 注文書生成
4. 受領 PDF をアップロード
5. 注文一覧で OCR を確認

詰まり:
- 月次メニュー登録後の影響範囲が見えにくい
- PDF アップロード後の遷移先が弱い
- 施設設定変更と個別注文修正が同じ画面にある

## 改善の実装順
1. TopNav を role-aware にする
2. `sheet_weekly_menu_missing` 中の確定ブロック
3. Step2 以降の precondition 表示と disabled 化
4. 注文書アップロード後の deep link 強化
5. admin 専用操作の折りたたみ/非表示

## 今回対応済み
- `TopNav` は `admin` グループを `admin` ユーザーにだけ表示
- `/auth/me` を追加し、frontend が現在ロールを取得可能にした
- `システム管理` と `送り状履歴` の admin 専用破壊操作は、operator には表示しない
- 注文詳細の Step2 以降は、施設/週が未設定・未保存の間はタブ遷移不可
- 注文詳細の `sheet_weekly_menu_missing` 中は確定不可
- 注文詳細の月次メニュー未登録警告から、対象月のメニュー編集へ直接移動できる

## テスト観点
- operator で見えてよいページだけが見える
- admin 専用ボタンは operator で表示されないか disabled
- 月次メニュー未登録時は確定できない
- Step1 未完了時は Step2/3 に進めない
- 注文書アップロード後に新規/既存注文へ必ず辿れる

## 備考
- 2026-03-12 時点では、backend API の権限そのものより frontend の見せ方と導線が主な問題
- 実ロールは `operator / admin` であり、`ユーザー1 / ユーザー2` は運用上の役割名として扱うのが自然
