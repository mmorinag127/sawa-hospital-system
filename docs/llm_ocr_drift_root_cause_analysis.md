# LLM OCR揺れによるシートズレ: 原因分析ドキュメント

## 目的
- 「なぜ注文ごとにズレるのか」「なぜ毎回デバッグになるのか」を、LLM出力揺れと実装責務の境界で整理する。
- 今回の実障害を再発させないため、原因を仕様レベルで固定する。

## 対象インシデント
- 注文: `ORDbabf3c73`
- 事象: LLM再解析後、`2/15 夕 チンゲン菜のお浸し` など一部行で全施設数量が空欄化。
- 追加観測:
  - 再解析メトリクス上は `before_count == after_count` で「変更なし」に見えるケースがある。
  - 実データでは LLM生出力に数量が存在するのに、`ocr-sheet` で欠落するケースがある。

## 事実ベースの発生メカニズム
1. LLMは行ごとに `date/daypart/menu/qty` を返すが、`daypart` 境界（朝昼夕）や日付は揺れる。
2. 週メニュー位置補正が `menu_name` のみ上書きし、`date/daypart` を残す実装だと、行キーが分裂する。
3. シート代入側は `date + daypart + menu` 一致を優先するため、キー不一致行の数量が未代入になる。
4. 結果として「LLMは数量を出したがシートは空欄」という症状が発生する。

## 根本原因（責務分離の失敗）
- 直接原因:
  - 非数量フィールド（`date/daypart/menu`）の正準化を週メニューに固定し切れていなかった。
- 背景原因:
  - LLMを「数量抽出器」ではなく「行構造決定器」として扱う経路が残っていた。
  - 行マッチ結果の妥当性検証（不一致時のhard fail）が弱く、欠落がサイレントで通る。

## 「注文ごとに違う」ように見える理由
- すべて同一コードで処理していても、入力品質と分岐条件で経路が変わる。
- 主な差分要因:
  1. `week_id` 解決可否（週メニュー経路 vs OCRテーブル経路）
  2. `order_lines` の有無（保存済み数量優先か、payload救済か）
  3. LLM出力の欠落・短縮・表記揺れ（truncation, row shortfall）
  4. マッピング方式の選択（identity/source_row/payload_row）
- 重要点:
  - 経路が変わっても結果が同一になる設計でなければ、注文差として露呈する。

## LLM依存か、実装依存か
- LLM依存:
  - `date/daypart/menu` の揺れ、欠落、短縮応答は起こり得る（避けられない）。
- 実装依存:
  - 揺れを吸収し切れず、非数量フィールド不一致を許容して保存した点が本質。
- 判定:
  - 「トリガーはLLM揺れ、事故化した原因は実装の正準化不足」。

## 現状実装の到達点（コード確認ベース）
- 実装済み:
  1. LLM reparseで `strict_numeric_quantity_cell=true`, `zero_as_empty=false` を強制。
  2. 異常値上限（`max_quantity_abs`）を適用。
  3. 週メニュー経路での数量救済は `allow_heuristics=false`（数字のみ）。
  4. 位置補正で `menu_name` に加え `daypart/date` も週メニュー値で上書き。
- 未充足/要強化:
  1. 保存前に「正準キー完全一致」を強制するhard validationが不足。
  2. 「全施設空欄行」や「日付/食区分偏り」の異常検知を保存時に拒否できていない。
  3. 再解析デバッグで、送信プロンプトと検証失敗理由の完全追跡が不足。

## 再発防止の必須要件（原因から逆算）
1. 週メニューが解決できる注文では、`date/daypart/menu` は常に週メニュー由来に固定する。
2. OCR/LLMの救済対象は数量セルのみとし、非数量セルの変更を禁止する。
3. 保存前に canonical key 一致検証を実施し、不一致は保存失敗で返す。
4. 0は有効数量として保存し、blankと同一視しない。
5. 異常行（全施設空欄など）は警告で済ませず、閾値超過で再解析失敗扱いにする。

## まとめ
- 毎回デバッグが必要な状態は、運用問題ではなく設計問題。
- 対策の中心はプロンプト微調整ではなく、非数量フィールドの決定論化と保存前検証の強制。
