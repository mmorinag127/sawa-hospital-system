# Menu Editor Revision Contract

| Read endpoint | Read response | Mutating caller | Required request header | Success response |
| --- | --- | --- | --- | --- |
| `GET /base-menus` | `items`, opaque `revision` | `PUT /base-menus/{id}`, `POST /base-menus` | `If-Match: <revision>` | updated item or `created`, current `items`, current `revision` |
| `GET /menu-rules?rule_type={global|menu|facility}` | `rules`, opaque `revision` | `POST /menu-rules`, `PUT /menu-rules/{id}`, `DELETE /menu-rules/{id}` | `If-Match: <revision>` | saved `rule` or `deleted: true` |

`428` means the caller omitted `If-Match`. `409` means the read generation is stale, the token is invalid or only covers a filtered base-menu read, the base-menu source `MenuMaster.revision` set changed, or a concurrent CAS won. `GET /base-menus` records the explicit read query and coverage in its opaque revision: an unfiltered read has `cycle_day: null` and `full` coverage, while `GET /base-menus?cycle_day=N` has `partial` coverage. Tokens reject duplicate source keys and reject mismatched query/coverage pairs. `POST /base-menus` accepts only the exact full snapshot token because it replaces the collection and may delete rows; it never supplements omitted items from the request body. `GET /base-menus` captures both its collection revision and the exact canonical `MenuMaster` revisions through the same resolver used for its item defaults; SQLite begins an explicit read transaction at that shared snapshot entrance because `FOR UPDATE` alone does not provide a driver snapshot there. A save made from an older read must leave the collection and source snapshot unchanged. Stored and token revisions must be positive non-boolean integers; invalid source or scope revisions stop with an operator-visible conflict. `GET /menu-rules` returns its own scope revision without changing it. The server advances the scope generation in the same transaction as the mutation; any later failure rolls it back. The `0030` migration creates all required scope rows explicitly.

`menu_editor_revision_column_ownership` is the formal source of truth for `0030` revision-column ownership. Upgrade writes exactly one record for each of `base_menu_cycle_items.revision` and `menu_rules.revision`: `0030` when the migration added that column, or `preexisting` when a valid column already existed. Before downgrade performs DDL, it requires the exact metadata schema and both expected records with a recognized ownership value. Missing, extra, or invalid metadata stops downgrade without DDL. Downgrade removes only columns marked `0030`; it retains every preexisting `revision` column and its data. Runtime code does not repair or synthesize missing ownership metadata.

Normal rollback is limited to the recorded `0030` ownership: a database where both revision columns were added returns to its pre-0030 column layout, while a database where either column was preexisting removes only the 0030 tables and retains that column and every value in it.
