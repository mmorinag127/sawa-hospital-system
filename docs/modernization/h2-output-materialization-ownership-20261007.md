## Failure Class And Shared Entry

Old accepted output calculation could delete newer Bag/LabelRow/DeliveryNote rows and overwrite deterministic current files. The shared `_capture_output_adoption` / `_require_output_adoption` pair now carries the original execution input, accepted candidate, and complete bagging artifact snapshots. Calculation consumes the original accepted candidate/config/policy, not a final current recapture. Final rereads are comparisons only, never calculation inputs.

The order payload, execution input, selected accepted artifact and accepted-origin receipt are all read in the caller's same Session. `get_order_by_id` now accepts an optional read_session; existing callers retain their ordinary read-only behavior. Output capture uses it rather than reading a second Session's order payload.

Capture also checks the existing accepted-origin contract BEFORE calculation. An unconfirmed artifact requires the original bagging_input_proof, exact typed owned revision, bagging ID/materialization digest, and unchanged original input versions/PDF/config/physical entries/draft/evidence. It cannot receive a new current token as a substitute for missing original proof. For an explicitly selected confirmed snapshot, its stored digest, saved sheet, selected evidence/template, bagging candidate and actual materialized lines must match. This is an explicit confirmed-source branch, not missing-proof fallback. The full confirmed snapshot is carried and reread/locked only after the final workflow claim; capture performs no earlier related-row lock. Missing original proof and preexisting in-place sheet edits stop before artifact generation.

`build_outputs` captures at processing start when it owns the outer transaction. Explicit caller-owned transactions require the original adoption argument; neither public writer opens an independent write transaction inside a provided Session. `rebuild_bags` requires both original adoption and caller Session. The existing synchronous guard claims the exact original workflow revision (PostgreSQL lock / SQLite conditional update), locks related execution rows, and checks original order/evidence/draft/cache/PDF input versions plus typed config/physical input equality. Final workflow meta, full bagging artifact rows and accepted candidate are compared in the same transaction before deletions. Bagging receipt rows are refreshed and locked after the workflow claim. Insertions flush in that transaction; neither writer commits independently.

Frozen bagging-time accepted config/policy still drives quantities. The separate processing-start execution snapshot is authority for adoption, not a replacement source for enrichment. Zero/null recognition and existing terminal/receipt policies are unchanged. Missing accepted facility config now stops instead of supplying an empty config.

## Artifact Publication

Both preview and materialized generation use a unique UUID-owned directory, with existing order_labels.csv / order_delivery.xlsx / order_aggregate.csv basenames. They never overwrite the old deterministic current files. Only after the final guard does the same DB transaction publish the DeliveryNote file_uri and materialized rows. A failed export, stale guard, insertion failure or caller rollback cannot change committed DB references to the prior artifact. Files generated in an aborted private directory can remain unreferenced; no cleanup lifecycle or guessed business version was introduced.

Read download contracts: `api/outputs.py` output-path resolver, download_labels, delivery download, aggregate download and preview routes consume the returned generated path; download filenames are separately specified. Existing unique daily export paths provided the precedent. No frontend/download response schema was changed. Label rows and aggregate serialization remain unchanged.

## Actual Caller Audit

- `workers/output_worker.py`: `_run_outputs_inline` calls `build_outputs(order_id)`; enqueue inline/Celery paths reach it and now receive processing-start capture and a single owned adoption transaction inside the public writer. Existing worker catch/set_status/retry behavior was read, not edited in this bounded source unit; it is not claimed to be an original-owned terminal outcome guard. Parent must separately review that status/retry behavior, including retries after ownership conflicts.
- `order_service._rebuild_bags_for_override_scopes` is the only production direct `rebuild_bags` caller found by repository-wide Python search. Single scope delegates to it; upsert, bulk upsert and delete override commands call these scopes. Internal scopes accept explicit original adoption intents and one caller Session, reject missing/duplicate/nonmatching scope without mutation, then pass those same intents to rebuild in sorted order. Each writer runs one final original guard; there is no extra guard preflight or independent commit. A later order failure propagates through the caller transaction for rollback of earlier writes. They do not manufacture original revisions from current state. The existing guard does NOT advance revision: SQLite uses revision=revision and PostgreSQL FOR UPDATE. No revision+1 compensation or invented advancement was introduced.
- `api/orders.py`: upsert, bulk upsert and delete daily-output-overrides currently have no public per-order original-version binding. Per latest instruction all three service commands explicitly block BEFORE calling the separately committing daily override storage writer. API response is 409 with `daily_output_original_ownership_required`; existing overrides and current bags are not modified. No new map field, single If-Match convention or server-acceptance policy was chosen. Human choice of UI per-order version transport versus server acceptance remains pending; these commands are deliberately unavailable until that binding and atomic override/rebuild transaction are integrated.
- All production `daily_output_override_service.upsert_override/upsert_overrides/delete_override` references found are these three guarded service commands. Direct storage helpers were not changed or declared to have output ownership semantics.
- Retained external integration caller: `tests/integration/test_bagging_delivery_slots.py` directly invokes rebuild_bags without original input. It is not reported compatible/passing and requires migration to the explicit original-owned contract.
- Adjacent workflow materialization/invalidation sources read: `_materialize_confirmed_lines_from_candidate` retains its original configured input and synchronous fence; `_delete_materialized_downstream_rows_for_order` / `_delete_downstream_after_sheet_change` remain workflow-command invalidation, not calls to these writers. No changes or whole-workflow safety claim are made for those paths.
