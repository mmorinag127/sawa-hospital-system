# LLM OCR揺れ耐性: 対処方法の考察と実行指針

## 目的
- LLM出力揺れを前提に、数量欠落・日付ズレ・食区分ズレを事故化させない。
- 「注文ごとの差」を残さないため、処理責務を固定する。

## 設計原則（固定）
1. 構造の真実ソースは `weekly_menu + template`。
2. LLM/OCRの責務は数量候補抽出に限定する。
3. `date/daypart/menu` はLLM出力値を直接保存しない。
4. 保存前に不整合を検知したら fail-fast する。

## 対処方法の比較考察

### A. プロンプト強化のみで抑える
- 内容:
  - 出力形式を厳密化し、日付・食区分・メニューの揺れを減らす。
- 長所:
  - 実装変更が小さく、即時に試せる。
- 短所:
  - モデル更新・画像品質・トークン制限で再発する。
  - 根本的に「揺れゼロ」は達成不能。
- 判定:
  - 補助手段として有効だが主対策には不十分。

### B. LLMにフル行構造を返させ、後段で吸収
- 内容:
  - 返却は従来どおりフル行（`date/daypart/menu/qty`）。
  - 後段で正規化して不一致を修正。
- 長所:
  - 既存資産を活かしやすい。
- 短所:
  - 吸収ロジックが複雑化し、分岐が増える。
  - 「どこまで修正してよいか」の境界が曖昧になりやすい。
- 判定:
  - 過渡期は可。最終形としては不安定。

### C. LLMを数量抽出器に限定（推奨）
- 内容:
  - LLM出力は `row_index + quantity cells (+confidence)` に縮退。
  - 非数量フィールドは週メニュー/テンプレで常に決定。
- 長所:
  - 揺れの影響面を最小化できる。
  - テスト対象が明確で、回帰を固定しやすい。
- 短所:
  - row_index安定化の設計（表行対応）が必要。
- 判定:
  - 本件の再発防止として最も再現性が高い。

## 採用方針（実行）
- 方針:
  - Cを主軸、Aを補助として採用する。
- 具体化:
  1. 週メニュー解決時は `date/daypart/menu` を強制上書き。
  2. 数量救済は数値セル限定で、非数量列と行構造は不変。
  3. 保存前 validation で canonical key 不一致を拒否。

## 追加対処（未実装ギャップへの対応）

### 1) 保存前Hard Validation
- ルール:
  1. 全行で `canonical(date,daypart,menu)` が週メニューに含まれること。
  2. 存在しない施設列への数量は拒否。
  3. 非数量フィールドがOCR由来で変化した痕跡がある場合は拒否。
- 失敗時の返却:
  - `sheet_canonical_mismatch`
  - `sheet_quantity_column_unmapped`
  - `sheet_non_quantity_mutation_blocked`

### 2) 異常値・異常パターン検知
- 検知対象:
  1. 特定行で全施設数量が空欄（要注意）
  2. 日付または食区分の連続欠損
  3. 前回確定値との差分率が閾値超過
- 運用:
  - 警告ではなく、閾値超過時は reparse を failed 扱いにする。

### 3) デバッグ可観測性強化
- 追加保持:
  1. 送信プロンプト（必要ならマスク版）
  2. 生レスポンス
  3. 正規化後ペイロード
  4. validation失敗理由一覧
- UI表示:
  - `raw -> normalized -> persisted` の3段差分を同一画面で追跡可能にする。

## 実装計画（優先順位）

### P0（再発防止の必須）
1. `reparse_order` 保存前に canonical mismatch hard validation を追加。
2. 異常行（全施設空欄）の拒否条件を追加。
3. エラーコードをAPI契約に追加し、UIに明示表示。

### P1（安定化）
1. LLM出力スキーマを数量中心へ縮退（段階導入）。
2. row_index対応の厳格化（week menu行単位の固定対応）。
3. debug payloadに prompt/normalized/reject-reasons を追加。

### P2（品質維持）
1. 注文ゴールデンセットでの定期回帰。
2. 失敗パターン自動収集とテスト化の半自動化。
3. provider別の品質メトリクス可視化。

## テスト計画（詳細）

### ユニット
1. 位置補正が `menu/date/daypart` を必ず上書きする。
2. strict数量で `0` を保持し、混在文字/異常値を拒否する。
3. canonical mismatch が必ず検知される。

### 統合
1. `reparse -> save -> get_ocr_sheet` で non-quantity 不変を検証。
2. 週メニュー境界（朝昼夕・日付跨ぎ）で数量が欠落しないことを検証。
3. 実障害注文フィクスチャ（`ORDbabf3c73` 相当）を固定回帰化。

### 契約/API
1. 新エラーコードがHTTP 400で返ること。
2. debug payloadに必要フィールドが揃うこと。
3. `changed=true/false` 判定が digest だけでなく validation結果と整合すること。

### E2E/運用
1. 再解析後の「全施設空欄行率」が閾値内。
2. provider別の再解析成功率が閾値内。
3. デプロイ前後でゴールデン一致率が低下しない。

## CI/デプロイゲート（必須）
1. P0に紐づくユニット/統合/契約テストは必須ゲート化。
2. ゴールデン注文一致率が閾値未満ならデプロイ不可。
3. 新規障害は再現fixture + テストID追加を同一PR必須とする。

## 実行後の完了判定
1. 既知障害で数量欠落が再現しない。
2. canonical mismatch が保存前に確実に止まる。
3. 再解析デバッグ画面で原因追跡が1回で完結する。
